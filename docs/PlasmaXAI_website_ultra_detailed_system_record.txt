PLASMAXAI WEBSITE ULTRA-DETAILED SYSTEM RECORD
==============================================

Document purpose
----------------
This file is a deep technical record of the PlasmaXAI website system. It is intended to explain, in practical engineering detail, how the website is structured, how the frontend, backend, database, report generator, and inference service fit together, and how the trained PlasmaXAI model is integrated into the full doctor-facing clinical workflow.

This is not a short summary. It is a system-level implementation record of the current website architecture inside this repository.


1. SYSTEM INTENT
----------------
The PlasmaXAI website is not just a static research showcase. It is designed as a doctor-facing clinical review workspace for plasma-cell case analysis. The goal is to let a doctor or reviewer:

1. sign in to an individual account
2. create or upload a case
3. associate the case with a patient
4. run PlasmaXAI inference on the uploaded microscopy image
5. view prediction output and explainability cues in a clinically readable way
6. edit checklist items and report language before finalizing the case report
7. revisit the case later from the case history archive
8. manage patients, cases, settings, and profile information

This means the website is not only a frontend. It is a layered clinical product composed of:

- a Next.js web application
- a Python inference service
- a database and storage layer via Supabase when cloud mode is enabled
- a local persistence layer for offline/demo fallback
- a PDF clinical reporting engine

3. WEB APPLICATION ARCHITECTURE
-------------------------------
The doctor-facing web application lives in:

- apps/web/src/app
- apps/web/src/components
- apps/web/src/lib

The architecture follows a practical Next.js App Router structure:

- app: route definitions and server entrypoints
- components: UI modules and domain-specific widgets
- lib: shared logic, storage handlers, auth helpers, report generation, data access, inference bridge, and domain utilities

This is not strict classical MVC in the old Rails sense, but it is structurally similar to a modern React/Next separation:

- views = route pages + components
- controllers/actions = server actions in route folders
- models/data layer = Supabase queries, local stores, and normalization utilities

6. AUTHENTICATION AND USER IDENTITY
-----------------------------------
Auth logic lives in:

- apps/web/src/lib/supabase/auth.ts
- apps/web/src/lib/supabase/client.ts
- apps/web/src/lib/supabase/server.ts

There are two modes:

1. hosted/Supabase mode
2. local fallback mode

Hosted mode:
- uses Supabase Auth
- server and browser clients are created through @supabase/ssr helpers
- requireUser() ensures there is an authenticated user
- ensureDoctorProfile() upserts the doctor profile into the profiles table

Local mode:
- activates automatically if Supabase config is missing
- reads a selected doctor identity from the plasmaxai-demo-user cookie
- resolves a doctor from local storage rather than remote auth

Local doctor storage:
- apps/web/src/lib/local-doctors/store.ts

This allows the same UI to remain usable even when the production backend is unavailable.

- links images to cases
- stores storage_path, file_name, mime_type

predictions
- one prediction row per case
- stores predicted_class, confidence, risk_level, model_version

explanations
- one explanation row per case
- stores counterfactual_text

- stores generated report file path
- report type

- optional review routing table

Security:
- row level security is enabled
- policies are organization-aware
- the current organization is resolved through current_org_id()

This is a strong clinical multi-user database pattern because it isolates records per organization while still allowing multiple doctors inside the same org to access shared patient/case information.

9. CASE CREATION FLOW
---------------------
Case creation is implemented in:

- apps/web/src/app/(workspace)/new-case/actions.ts

Flow in local mode:
1. createLocalCase() is called
2. patient is upserted into the local patient store
3. image is stored under .local-data/uploads
4. local case JSON is updated
5. queueCaseInference() is called
6. if inference succeeds, updateLocalCaseInference() stores prediction and explanation
7. route revalidation occurs
8. user is redirected to /cases/[id]

Flow in Supabase mode:
1. requireUser() returns authenticated doctor
2. organization is resolved or created
3. patient is found or inserted
4. image is uploaded to Supabase Storage
5. case row is inserted
6. case_images row is inserted
7. queueCaseInference() is called
8. prediction and explanation tables are populated
9. PDF report is created and uploaded
10. reports row is inserted
11. audit_logs row is inserted
12. route revalidation occurs
13. doctor is redirected to the case page


10. INFERENCE BRIDGE
--------------------
The frontend does not directly execute PyTorch in the browser. Instead, the web app talks to an inference bridge:

- apps/web/src/lib/inference/service.ts

This bridge chooses one of two paths:

1. hosted inference API
2. local Python fallback

Decision logic:
- if INFERENCE_API_URL or INFERENCE_URL exists, it attempts HTTP fetch to the inference service
- if hosted inference fails and the environment allows local fallback, it executes local Python directly
- in hosted Vercel mode, local Python fallback is disabled by default unless explicitly allowed

This makes the system robust:
- good for local development
- compatible with Vercel services
- does not trap the UI when the hosted API is unavailable


11. INFERENCE SERVICE
---------------------
The Python inference API lives in:

- apps/inference/app/main.py
- apps/inference/app/predictor.py

FastAPI layer:
- defines /health
- defines POST /cases
- validates incoming payload using pydantic
- returns the fully structured inference payload expected by the web app

Core predictor:
- class PlasmaXAIPredictor in predictor.py

This predictor loads:
- operating point JSON
- fusion scalers
- counterfactual bundle
- summary/config JSON
- resnet50 checkpoint
- densenet121 checkpoint
- novel fusion checkpoint

The predictor pipeline:
1. fetch image bytes from URL, local path, or Supabase authenticated storage
2. decode RGB image
3. transform image into model tensor
4. extract morphology features
5. compute resnet embedding and probability
6. compute densenet embedding and probability
7. scale morphology vectors
8. compute counterfactual-space features
9. compute score features
10. run the CounterfactualGuidedFusionNet
11. softmax outputs into plasma probability
12. compute modality gates
13. determine risk level using threshold
14. create doctor-facing explanation fields
15. return final structured result


12. MODEL INTEGRATION LAYER BY LAYER
------------------------------------
The deployed PlasmaXAI inference path is a multi-branch fusion system.

The fusion model defined in predictor.py is:
- CounterfactualGuidedFusionNet

Branches and internal roles:

1. ResNet branch
- input: ResNet embedding
- layer block: LayerNorm -> Linear -> GELU -> Dropout
- purpose: capture strong image-pattern features from the microscopy image

2. DenseNet branch
- input: DenseNet embedding
- layer block: LayerNorm -> Linear -> GELU -> Dropout
- purpose: capture texture-sensitive image features and complementary CNN context

3. Morphology branch
- input: engineered morphology vector
- layer block: LayerNorm -> Linear -> GELU -> Dropout
- purpose: represent explicit tabular cytomorphology features

4. Counterfactual branch
- input: counterfactual-space vector built from margin, delta, and prototype shift
- layer block: LayerNorm -> Linear -> GELU -> Dropout
- purpose: express how far the sample is from the benign decision region and which features would have to move to lower suspicion

5. Score branch
- input: compact score vector derived from model outputs
- layer block: LayerNorm -> Linear -> GELU -> Dropout
- purpose: preserve calibrated score-level summary signals

Cross-branch control:
- cf_to_res: counterfactual-conditioned gate into the ResNet feature path
- cf_to_den: counterfactual-conditioned gate into the DenseNet feature path
- morph_to_scores: injects morphology-plus-counterfactual context into the score stream

Modality gate:
- concatenates res, den, morph, cf, score features
- runs LayerNorm + Linear
- applies softmax over 4 gating outputs
- dynamically weights:
  - resnet branch
  - densenet branch
  - morphology branch
  - counterfactual branch

Fusion:
- weighted branch combination produces fused_modal
- fused_modal is concatenated with the unified score branch
- classifier head:
  - LayerNorm
  - Linear
  - GELU
  - Dropout
  - Linear to 2 classes

This is the actual mechanism that connects image embeddings, morphology vectors, and counterfactual reasoning into one deployable decision path.

It uses pdf-lib and builds the report procedurally.

Report generation flow:
1. gather case metadata
2. gather prediction result
3. gather explanation result
4. gather report draft edits if present
5. gather review checklist items if present
6. embed microscopy image
7. draw structured PDF sections

Important report sections:
- title and case identity
- clinical case context
- microscopy review image
- focus map and microscopy overlay
- explainability diagrams
- clinical review summary
- doctor-facing interpretation
- what would lower suspicion
- recommended doctor actions
- doctor review checklist

The current report generation path already accepts:
- reportDraft
- reviewChecklist

That means doctor edits from the case page can flow into the generated report, rather than treating the PDF as a fixed model output.

18. LOCAL MODE VS HOSTED MODE
-----------------------------
This website supports two operating modes.

Local mode:
- no Supabase required
- local JSON and file stores
- local doctors
- local case images
- local reports
- optional local Python inference fallback

Hosted mode:

This dual-mode design is one of the biggest practical strengths of the system because:
- it is demo-friendly
- it is resilient during setup

20. END-TO-END DATA FLOW
------------------------
Full hosted case flow:

1. doctor signs in
2. auth session is available to the Next server layer
3. doctor creates a patient or selects an existing one
4. doctor uploads microscopy image
5. image is stored in Supabase Storage
6. case row is created
7. image metadata row is created
8. inference bridge posts to /api/inference/cases
9. inference service loads PlasmaXAI and analyzes the case image
10. structured result returns:
    - predicted class
    - confidence
    - risk level
    - probabilities
    - modality gates
    - morphology vector
    - top features
    - counterfactual text
    - clinical insight text
11. web app stores prediction row
12. web app stores explanation row
13. web app generates PDF report
14. PDF uploaded to report bucket
15. report row stored
16. case page reads all of that back into the doctor-facing review UI
17. doctor edits notes, checklist, and report summary
18. doctor finalizes and downloads report
19. case remains accessible through history and patient timeline
