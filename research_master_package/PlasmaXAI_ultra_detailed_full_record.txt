1. Project identity, final name, and scope
------------------------------------------------------------------------------
Final preferred name:
PlasmaXAI

Earlier names used during development:
- PlasmaXNet
- PLASMAXNET

Final identity:
PlasmaXAI is a counterfactual-guided explainable AI framework for malignant
plasma-cell recognition in multiple myeloma microscopy images. It is not only
a classifier. It is a research-and-translation package consisting of:
- a notebook baseline
- an optimization-stage benchmark system
- a final learned fusion framework
- explainability assets
- patient-level exploratory analyses
- paper and diagram materials
- a doctor-facing website
- a separate inference service


2. Clinical and scientific background
------------------------------------------------------------------------------
Multiple myeloma is a hematologic malignancy driven by abnormal plasma-cell
proliferation. Morphologic review still matters because plasma-cell appearance,
burden, and organization remain relevant during diagnosis, disease monitoring,
and treatment-oriented interpretation.

Why this problem matters:
- manual review is labor intensive
- interpretation depends heavily on expertise
- stain variability and morphology variation complicate consistency
- large-scale screening is difficult to scale manually
- many AI systems optimize accuracy but do not help doctors understand the
  output

PlasmaXAI was designed to address that gap. The project tries to answer:
"Can an explainable, high-performing plasma-cell recognition system be built
that improves diagnostic support while presenting evidence in a form useful to
doctors rather than only to ML developers?"


3. Research objectives
------------------------------------------------------------------------------
Primary objectives:
1. Build a strong malignant plasma-cell recognition framework on PCMMD.
2. Improve over the earlier notebook-stage baseline.
3. Compare against deep and morphology-based baselines.
4. Move explainability into the decision pathway itself.
5. Add patient-level consistency analysis.
6. Package the work into paper-ready figures, reports, and a doctor-facing
   website.

Secondary objectives:
- improve plasma precision and recall simultaneously
- support claims with ablation and bootstrap evidence
- package the work for competition judging and deployment presentation

10. Final novel architecture overview
------------------------------------------------------------------------------
Main pipeline:
F:\BUET plasma\novel_plasmaxai_pipeline.py

Main final checkpoint:
F:\BUET plasma\novel_outputs\novel_fusion_model.pth

Supporting artifacts:
- fusion_scalers.joblib
- counterfactual_bundle.joblib
- novel_summary.json
- plasmaxai_operating_point.json

High-level idea:
The final model combines:
1. ResNet50 image embeddings
2. DenseNet121 image embeddings
3. handcrafted morphology
4. counterfactual boundary descriptors
5. compact score features

These are passed through separate encoders, modulated by counterfactual
signals, dynamically reweighted by a learned gate, fused, and finally
classified.

12. Layer-by-layer novel architecture
------------------------------------------------------------------------------
The final architecture class is `CounterfactualGuidedFusionNet`.

Final best configuration:
- hidden_dim = 256
- tabular_dim = 128
- dropout = 0.25

12.1 ResNet encoder
Input:
- 2048-dimensional ResNet embedding

Layers:
1. LayerNorm(2048)
2. Linear(2048 -> 256)
3. GELU
4. Dropout(0.25)

Output:
- 256-dimensional ResNet latent vector

12.2 DenseNet encoder
Input:
- 1024-dimensional DenseNet embedding

Layers:
1. LayerNorm(1024)
2. Linear(1024 -> 256)
3. GELU
4. Dropout(0.25)

Output:
- 256-dimensional DenseNet latent vector

12.3 Morphology encoder
Input:
- 10-dimensional morphology vector

Layers:
1. LayerNorm(10)
2. Linear(10 -> 128)
3. GELU
4. Dropout(0.25)

Output:
- 128-dimensional morphology latent vector

12.4 Counterfactual encoder
Input:
- 24-dimensional counterfactual feature vector

Layers:
1. LayerNorm(24)
2. Linear(24 -> 128)
3. GELU
4. Dropout(0.25)

Output:
- 128-dimensional counterfactual latent vector

12.5 Score encoder
Input:
- 3-dimensional score vector:
  - ResNet probability
  - DenseNet probability
  - counterfactual logistic probability

Layers:
1. LayerNorm(3)
2. Linear(3 -> 128)
3. GELU
4. Dropout(0.25)

Output:
- 128-dimensional score latent vector

12.6 Counterfactual-to-ResNet gate
Module:
- Linear(128 -> 256)
- Sigmoid

Operation:
`res_feat = res_feat * cf_to_res(cf_feat)`

Meaning:
The counterfactual branch directly modulates the ResNet branch. This is one of
the main reasons the architecture is more than a post-hoc explanation system.

12.7 Counterfactual-to-DenseNet gate
Module:
- Linear(128 -> 256)
- Sigmoid

Operation:
`den_feat = den_feat * cf_to_den(cf_feat)`

Meaning:
The DenseNet latent representation is also explicitly filtered through a
counterfactual gate.

12.8 Morphology-to-score refinement
Module:
- Linear(128 + 128 -> 128)
- GELU
- Dropout(0.25)

Input:
- concatenation of `morph_feat` and `cf_feat`

Operation:
`score_feat = score_feat + morph_to_scores(concat(morph_feat, cf_feat))`

Meaning:
The score branch does not remain a raw three-number channel. It becomes a
learned, morphology-aware, counterfactual-aware signal.

12.9 Modality gate context
The gate context is the concatenation of:
- res_feat (256)
- den_feat (256)
- morph_feat (128)
- cf_feat (128)
- score_feat (128)

Total dimension:
- 896

Modality gate module:
1. LayerNorm(896)
2. Linear(896 -> 4)
3. Softmax

Output:
- four gate weights

These correspond to:
- ResNet branch
- DenseNet branch
- morphology branch
- counterfactual branch

12.10 Unification layers
To bring branch outputs into a common fusion space:
- res_unify: Linear(256 -> 256)
- den_unify: Linear(256 -> 256)
- morph_unify: Linear(128 -> 256)
- cf_unify: Linear(128 -> 256)
- score_unify: Linear(128 -> 256)

12.11 Fused modal stream
The fused modal vector is built as:
- gate_resnet * res_unify(res_feat)
- plus gate_densenet * den_unify(den_feat)
- plus gate_morph * morph_unify(morph_feat)
- plus gate_cf * cf_unify(cf_feat)

This yields one 256-dimensional fused modal representation.

12.12 Final classifier path
The unified score branch is:
- score_unify(score_feat) -> 256 dimensions

The final classifier input is:
- concat(fused_modal, score_unify(score_feat))

Total classifier input dimension:
- 512

Classifier layers:
1. LayerNorm(512)
2. Linear(512 -> 256)
3. GELU
4. Dropout(0.25)
5. Linear(256 -> 2)

Outputs:
- binary logits
- modality gates

12.13 Forward-path summary
The exact logic is:
1. encode all five input blocks
2. gate both deep image streams using counterfactual features
3. refine the score stream using morphology + counterfactual context
4. compute softmax modality weights from all streams
5. project each branch to a common 256-dimensional space
6. form a weighted modal sum across ResNet/DenseNet/Morphology/Counterfactual
7. concatenate the weighted modal sum with the score stream
8. classify into two classes

This is the central architectural novelty of PlasmaXAI.


13. Morphology feature extraction details
------------------------------------------------------------------------------
Each image is resized to 128 x 128 for handcrafted morphology extraction.

Computed channels:
- mean_r = average red intensity / 255
- mean_g = average green intensity / 255
- mean_b = average blue intensity / 255

Staining intensity:
- 1.0 - mean(image) / 255

Grayscale conversion:
- RGB -> grayscale

Thresholding:
- nucleus mask uses threshold 80 with binary inverse
- cell mask uses threshold 200 with binary inverse

Area quantities:
- nucleus_area = positive nucleus pixels / total pixels
- cell_area = positive cell pixels / total pixels
- cytoplasm_area = max(cell_area - nucleus_area, 0)

NC ratio:
- nucleus_area / max(cytoplasm_area, 1e-3)
- clipped at 25.0

Granularity:
- Laplacian variance / 1000

Roundness:
- computed from the largest nucleus contour using:
  (4 * pi * area) / perimeter^2

The final morphology block is:
- nc_ratio
- nc_ratio_log1p
- nucleus_area
- cytoplasm_area
- staining_intensity
- granularity
- roundness
- mean_r
- mean_g
- mean_b


14. Backbone feature extraction details
------------------------------------------------------------------------------
Backbones used:
- ResNet50
- DenseNet121

Checkpoint sources:
- optimization_outputs/checkpoints/resnet50_final.pth
- optimization_outputs/checkpoints/densenet121_final.pth

Image preprocessing for the backbones:
1. resize to 224 x 224
2. convert to tensor
3. normalize with ImageNet statistics:
   - mean [0.485, 0.456, 0.406]
   - std [0.229, 0.224, 0.225]

Feature extraction logic:
- `forward_features(images)`
- `forward_head(feat_map, pre_logits=True)` -> embedding
- `forward_head(feat_map)` -> logits
- softmax(logits)[:, 1] -> plasma probability

Cached embedding files:
- novel_outputs/cache/train_embeddings.pkl
- novel_outputs/cache/val_embeddings.pkl
- novel_outputs/cache/test_embeddings.pkl

Observed cache sizes:
- train_embeddings.pkl ~ 61.3 MB
- val_embeddings.pkl ~ 13.2 MB
- test_embeddings.pkl ~ 13.2 MB

Why caching mattered:
Backbone features were expensive enough that reusing cached embeddings made the
fusion search and repeated analysis stages much faster and more stable.


15. Counterfactual model and counterfactual feature construction
------------------------------------------------------------------------------
Counterfactual model fitting uses:
- StandardScaler
- LogisticRegression(max_iter=2000, class_weight="balanced", random_state=42)

Training morphology data:
- the training split morphology table only

Stored counterfactual bundle contents:
- scaler
- logistic regression model
- benign prototype

Counterfactual features are constructed by:
1. scaling morphology features
2. computing logistic margin
3. computing logistic plasma probability
4. reading the logistic coefficient vector
5. forming the shift-to-boundary vector `delta`
6. forming the shift-to-benign-prototype vector `proto_delta`

The final 24-dimensional counterfactual block includes:
- 10 `cf_shift_*` values
- 10 `proto_shift_*` values
- cf_margin
- cf_distance_l2
- cf_distance_l1
- cf_proto_distance

This block is one of the defining parts of the final model because it gives a
mathematically structured explanation-aware representation of how far the
sample lies from a lower-risk morphology region.


16. Training logic for the fusion model
------------------------------------------------------------------------------
Training dataset object:
- TensorDataset(res, den, morph, cf, scores, labels)

Class balancing strategy:
- inverse-frequency weights
- WeightedRandomSampler
- class-weighted CrossEntropyLoss

Optimizer:
- AdamW

Scheduler:
- CosineAnnealingLR with `T_max = epochs`

Mixed precision:
- torch.autocast used on CUDA
- torch.amp.GradScaler used on CUDA

Early stopping:
- based on validation priority
- patience from the config

Config search space:

- fusion_cfg_b
- fusion_cfg_c

Best config selected:

- tabular_dim = 128
- dropout = 0.25
- lr = 0.001
- weight_decay = 0.0001
- epochs = 60
- batch_size = 128
- patience = 10


17. Threshold search and model selection logic
------------------------------------------------------------------------------
Threshold search is performed on validation probabilities using:
- `np.linspace(0.05, 0.95, 181)`

That means the threshold is scanned in 0.005 increments.

Metrics computed at each threshold:
- accuracy
- weighted F1
- plasma precision
- plasma recall
- AUC

The priority rule is not just "highest accuracy". The model selection logic
first checks whether plasma recall reaches a clinical floor of 90%. The
priority tuple is:
1. recall floor met or not
2. accuracy
3. weighted F1
4. AUC
5. plasma recall

This is extremely important for understanding how the final result was
produced. The model was selected with a clinical screening mindset rather than
with a purely academic top-1 accuracy mindset.

28. Limitations
------------------------------------------------------------------------------
Scientific limitations:
- no external multi-center validation
- patient-level cohort is very small
- same-source exploratory patient analysis can be optimistic

Deployment limitations:
- hosted persistence requires proper Supabase configuration
- local fallback mode is for local evaluation, not production persistence
- PyTorch inference on Vercel can still be operationally constrained

Claim boundary:
The strongest honest claim is not "fully clinically proven".
The strongest honest claim is:
"PlasmaXAI is a high-performing, explainable, counterfactual-guided
plasma-cell screening framework with a credible path toward clinician-in-the-
loop deployment."

32. Step-by-step walkthrough of how one final result was produced
------------------------------------------------------------------------------
This section explains, step by step, how a single final reported PlasmaXAI
test result was actually generated in practice.

Step 1: Dataset load
The pipeline starts by scanning the Set 1 folder under `PCMMD_LOCAL/set1` and
collecting file paths for the class folders defined in `CLASS_NAMES`. Every
valid image path is stored together with:
- the path
- numeric label
- class name
- image_id

Step 2: Train/validation/test split
The full dataframe is split with stratification. This is important because it
ensures the class distribution is preserved across train, validation, and test
partitions. The split uses a fixed seed, so the result is repeatable for the
same environment and input data.

Step 3: Morphology extraction
Every image in the full dataset has morphology features extracted and cached to
`segmentation_morph_features.csv`. This cache avoids recomputing handcrafted
features every time the fusion search runs.

Step 4: Counterfactual model fitting
Only the training portion of the morphology table is used to fit the
logistic-regression-based counterfactual boundary model. This is important for
keeping the decision-boundary logic properly inside the training data regime.

Step 5: Counterfactual feature computation
Counterfactual features are then computed separately for training, validation,
and test. This produces per-sample boundary-distance and prototype-shift
descriptors that eventually become part of the final neural input.

Step 6: Backbone embedding extraction
The training, validation, and test splits are passed through ResNet50 and
DenseNet121. Their pre-logit embeddings and probabilities are extracted and
cached to pickle files. These features are then merged with morphology and
counterfactual data.

Step 7: Fusion search
The pipeline trains several candidate fusion configurations. For each epoch in
each candidate configuration, it:
- trains on the training set
- evaluates on the validation set
- searches validation thresholds
- stores the epoch metrics and mean gate values
- keeps the best state according to the validation priority rule

Step 8: Best-model selection
After all configurations finish, the best configuration is selected by the same
clinical priority logic used during validation.

Step 9: Held-out test evaluation
The best fusion model is evaluated on the held-out test set. The model outputs
probabilities and gate values. The selected threshold is applied to generate
class predictions and compute final metrics.

Step 10: Comparison and packaging
The test metrics are then compared with baseline systems, written to JSON/CSV,
used for plotting, and later refined into the final preferred threshold at
0.72.


33. Detailed explanation of the training loop and optimization dynamics
------------------------------------------------------------------------------
The training loop in `train_fusion_model` is worth documenting carefully
because it shows how the final result was stabilized.

33.1 Weighted sampling
The class distribution of the training data is converted into inverse class
weights. These weights are used twice:
- first to build `sample_weights` for the `WeightedRandomSampler`
- second to build class weights for the final `CrossEntropyLoss`

This means minority-class underrepresentation is addressed both in which
examples appear during training and in how loss penalizes mistakes.

33.2 Mixed precision
Whenever CUDA is available, the training loop uses:
- `torch.autocast`
- `torch.amp.GradScaler`

This accelerates training and reduces memory pressure on the GPU. Because the
project was run on an RTX 3060 with 12 GB of VRAM, mixed precision helps keep
training efficient while still allowing sufficiently large batch sizes.

33.3 Optimizer choice
`AdamW` is used rather than plain SGD or vanilla Adam. This is a sensible
choice for a mixed tabular-deep fusion network because:
- it is effective for dense parameter optimization
- decoupled weight decay often behaves more cleanly than naive L2 treatment
- it is widely used for transformer-like and hybrid deep architectures

33.4 Scheduler choice
`CosineAnnealingLR` is used with `T_max = epochs`. This means the learning rate
gradually anneals over the full training horizon rather than stepping down at a
few abrupt milestones. For compact fusion heads trained on frozen deep
embeddings, this often gives a smoother optimization trajectory than a harsh
piecewise schedule.

33.5 Best-state retention
The training loop does not simply keep the final epoch. Instead, it stores the
state dictionary of the best validation state seen so far. That state is later
reloaded into the model before returning the training result. This is important
because it ensures the test set is evaluated using the validation-best fusion
parameters rather than the last epoch by default.

33.6 Patience and stopping
The loop increments `bad_epochs` whenever the validation priority fails to
improve. Once `bad_epochs` reaches the configured patience, training stops. In
practice, this prevents wasting compute on epochs that are no longer improving
the model meaningfully.

35. Detailed explanation of patient-level crop processing
------------------------------------------------------------------------------
The patient-level analysis is easy to misread as if it were a simple table
aggregation, but there is real image processing behind it.

35.1 Patient directory structure
The pipeline expects patient folders whose names start with `patient`.
Inside each patient folder, it expects:
- an `images` directory
- a `labels` directory

The labels are text files aligned with the images.

35.2 Label parsing
Each label line is interpreted as:
- class id
- x-center
- y-center
- bounding-box width
- bounding-box height

These are treated as normalized coordinates and are transformed into pixel
coordinates using the image width and height.

35.3 Padding strategy
After the crop is computed from the bounding box, 10% padding is added in both
the x and y directions. This is important because cell context around the
bounding box may still carry useful morphology and stain information.

35.4 Crop extraction and filtering
If the crop is empty, the sample is skipped. Otherwise the crop is retained and
stored as an RGB array. This means the patient-level inference stage runs on
true extracted cell crops rather than on metadata only.

35.5 Consistency analysis
For plasma-positive cells within a patient, the code computes pairwise cosine
similarity of the counterfactual-shift vectors. This creates a patient-level
consistency value that summarizes whether malignant-like counterfactual
movements are coherent across plasma cells in the same patient.

That is one of the reasons the patient-level analysis is scientifically
interesting despite being exploratory.

38. Vercel deployment implementation details
------------------------------------------------------------------------------
The Vercel readiness work was not only a documentation change; it required code
changes to make hosting behavior honest and safer.

38.1 Website-side hosted inference behavior
Originally, the website could fall back to running the local Python inference
script. That is useful for local development but not appropriate for a hosted
Vercel deployment. The website inference service helper was therefore changed
to:
- use `INFERENCE_API_URL` when provided
- allow local fallback only outside hosted deployment
- return a clean "not configured" reason if hosted inference is unavailable

38.2 Inference-service Vercel entrypoint
Vercel’s FastAPI support expects a supported entrypoint. An explicit
`app/app.py` wrapper was therefore added so the service exposes its FastAPI app
in a Vercel-compatible location.

38.3 Model-asset staging
Because the model artifacts live outside the inference folder in the repo,
`build.py` was added to stage the required files into `model_assets/` during a
hosted build. This is a practical deployment step, not just a documentation
note.

38.4 Function limits
`vercel.json` was added on the inference side to give the Python function a
larger memory and duration budget. This does not solve every production
constraint, but it makes the deployment more realistic.
